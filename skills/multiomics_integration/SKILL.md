# Multi-omics Integration Skill

## 1. Purpose

This Skill guides Codex / Agent workflows for integrating standardized evidence
from transcriptomics, metabolomics, and genomics/GWAS modules into unified
candidate results.

The integration step converts one or more module-level `standardized_evidence.tsv`
files into:

- `integration/candidate_gene_table.tsv`
- `integration/recommendation_report.md`

This Skill does not run raw bioinformatics analyses. It only processes
standardized evidence tables that have already been generated by upstream omics
modules.

## 2. Inputs

Expected inputs may include:

- transcriptomics `standardized_evidence.tsv`
- metabolomics `standardized_evidence.tsv`
- genomics/GWAS `standardized_evidence.tsv`
- `trait`
- optional phenotype file
- optional literature evidence

Each upstream omics module is responsible for producing its own evidence rows
before integration begins.

## 3. Required Evidence Schema

Every `standardized_evidence.tsv` file must use the same schema:

- `entity_id`
- `entity_type`
- `omics_type`
- `trait`
- `comparison`
- `direction`
- `effect_size`
- `p_value`
- `adj_p_value`
- `evidence_score`
- `source_module`
- `source_file`
- `evidence_note`

All omics modules must output this schema before they can be connected to the
integration module. If one module uses a different schema, normalize it first
rather than adding special-case logic to the integration report.

## 4. Outputs

The integration workflow should produce or update:

- `integration/standardized_evidence.tsv` or multiple evidence files
- `integration/candidate_gene_table.tsv`
- `integration/recommendation_report.md`
- `manifest.json`
- `run.log`

The manifest should record the generated candidate table and recommendation
report so downstream CLI, Gradio, and review workflows can find them reliably.

## 5. Candidate Aggregation Rules

First-version candidate aggregation rules:

- Aggregate evidence by `entity_id`.
- Count distinct `supporting_omics` values after de-duplication.
- Use `evidence_score` as the main candidate ranking signal.
- Higher numbers of supporting omics should increase the recommendation level.
- When only transcriptomics evidence is available, the output should remain a
  preliminary candidate explanation and should not become a final breeding
  recommendation.

The aggregation design must support future metabolomics and genomics/GWAS
evidence, even when the current project only has transcriptomics evidence.

## 6. Recommendation Rules

LLM or report modules must not directly turn raw numeric tables into final
breeding recommendations.

Recommendations must be based on:

- standardized evidence
- candidate table
- phenotype evidence
- literature evidence

If phenotype evidence and literature evidence are missing, the report should
only provide candidate explanations, evidence summaries, limitations, and
follow-up validation suggestions.

## 7. Common Mistakes

Avoid these mistakes:

- Directly asking an LLM to inspect a raw DEG table and give breeding advice.
- Failing to unify the evidence schema across omics modules.
- Treating a user-input `trait` as a validated phenotype conclusion.
- Ignoring provenance such as `source_module`, `source_file`, and
  `evidence_note`.
- Failing to distinguish candidate explanation from final breeding
  recommendation.
- Overstating conclusions while metabolomics or genomics/GWAS modules are still
  placeholders and not yet connected.

## 8. Test Command

Current available test:

Run the Transcriptomics DEG Module first to generate:

- `integration/standardized_evidence.tsv`
- `integration/candidate_gene_table.tsv`

Then inspect:

- `integration/recommendation_report.md`

The report should clearly state that current evidence is transcriptomics-only
and should provide candidate explanations rather than final breeding
recommendations.
